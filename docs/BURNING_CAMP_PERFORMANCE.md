## Change and comparison

The baseline is master `b53ddf0`, retained as `build/fire-perf/before-game`. The new code
was measured on `sol2/work` on 2026-10-09, GTX 1070 / i7-6700 (4 cores, 8 threads).
Scenario: `BOTW_SKIP=1 BOTW_TENTFIRE=5 BOTW_AT="-955,1964,0"`. Each process advances the
same fixed-step simulation, including grass spread, tent collapse and burning-tree effects.
All renders, including the entire repeat suite, hold `flock /tmp/botw-render.lock`.
The 960-frame runs flush the final raw batch so all 660 intervals 241–900 are available.
GPU/CPU runs explicitly use `BOTW_NOVSYNC=1 SLOPPY_PLATFORM=x11`; paced runs use Wayland.
GPU timer queries are nonblocking. No unfinished query frames were reported in the nine
final runs. GPU and paced outputs differ; they are compared within their own backend.

Terrain coverage now draws first in a cheap depth pass, including the existing cave cut.
Buildings/trees then populate depth before the ground's expensive shader uses `GL_EQUAL`.
That shader has no discard, allowing early rejection of covered terrain; forest/road noise
with exactly zero contribution is skipped. Dedicated shadow shaders retain the closed hill.
Burn-map writes dirty only changed quantized bytes, and all terrain passes share one tightly
packed dirty-rectangle upload per frame. A headless probe checked saturation, clipped edges,
channel separation and negative decay; game screenshot comparisons check the resulting map.

Smoke uses a half-resolution HDR target with premultiplied color/opacity, full-resolution
opaque depth for soft intersections and one composite. Transparent sprite corners skip noise
and depth reads. Conservative particle visibility tests reduce draw payloads while preserving
spawn rates, lifetimes, random-number consumption and fire propagation. Flames, embers, rain,
leaf sprites, water rings and contact shadows retain full scene resolution. `BOTW_FX_FULLRES=1`
selects the full-resolution smoke path for profiling and image comparisons.

## Presentation investigation

`game/frametime.jo` preserves the earlier raw columns and adds `runtime_present_ms`,
`gap_minus_present_ms` and thread CPU between drawing completion and the next update.
The first comes directly from the runtime's preceding `__platform_present` call, instead of
inferring it from GPU timers or labelling all gap time as presentation. The remaining gap
contains submission, audio/polling, diagnostic output and scheduling. Main-thread wall/CPU
and context switches continue to distinguish preemption/blocking from actual CPU work.

Baseline paced p95 is **33.69 ms** over the same intervals 241–900.
Final paced median p95 is **17.36 ms** (17.16–18.37), close to the requested 17 ms.
Presentation tails remain: repeat 1, interval 775 is **34.229 ms**, containing **5.003 ms**
game work, **28.940 ms** runtime presentation and **0.286 ms** residual gap, with **4.930 ms**
game thread CPU and no game-frame context switches. It is a measured presentation wait;
these logs do not distinguish compositor pacing, buffer/driver waits and scheduling inside
that call. The residual gap's three-run median p95 is **0.342 ms**. CPU-profiled X11 repeat 1,
interval 646 instead contains **30.079 ms** game wall time / **19.360 ms** thread CPU with
2 voluntary and 2 involuntary switches, and only **0.654 ms** presentation. Both classes
remain visible; GPU savings do not prove that every delivery hitch has disappeared.

Reproduce the separated suite:

```sh
BENCH_VIEW="burning tent" BENCH_MODES="paced gpu cpu" BENCH_REPEATS=3 \
  BENCH_JSON=docs/fire-benchmarks.json tools/bench.sh
```

`BENCH_VIEW` selects an exact scenario name. Default suites now include the tent fire and run
960 frames; choosing that scenario with fewer than 960 frames fails explicitly. Each run
retains its own screenshot. `--report` can rebuild reports from captured logs, including older
ten-view suites when `BENCH_FRAMES=480` is supplied. CPU profiles and visible particle counts
are retained in the JSON alongside raw slow samples and process/load diagnostics.
